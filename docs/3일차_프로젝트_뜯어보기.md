# 3일차 프로젝트 템플릿 뜯어보기

## 1. 프로젝트 개요

이 프로젝트는 FastAPI를 기반으로 만든 헬스케어 웹 백엔드 프로젝트이다.

프로젝트의 기능을 역할별 폴더로 나누어 관리하며, SQLAlchemy를 사용하여 데이터베이스 모델을 작성한다.

작성한 데이터베이스 모델의 변경 사항은 Alembic을 사용하여 실제 데이터베이스에 적용한다.

---

## 2. 디렉터리 역할

### app/core/

프로젝트 전체에서 공통으로 사용하는 설정과 기본 기능을 관리하는 폴더이다.

주로 다음과 같은 내용을 작성한다.

- 데이터베이스 연결 설정
- 환경변수 설정
- 프로젝트 공통 설정
- 여러 기능에서 함께 사용하는 기본 코드

쉽게 말하면 `app/core/`는 프로젝트의 기본 환경을 관리하는 폴더이다.

---

### app/models/

데이터베이스에 어떤 테이블과 컬럼을 만들지 정의하는 폴더이다.

주로 SQLAlchemy ORM을 사용하여 다음 내용을 작성한다.

- 테이블 이름
- 컬럼 이름
- 컬럼의 데이터 타입
- 기본키
- 외래키
- 다른 테이블과의 관계

예를 들어 환자 정보를 저장하는 테이블이라면 환자 ID, 이름, 성별, 생년월일 등의 컬럼을 모델로 작성할 수 있다.

쉽게 말하면 `app/models/`는 데이터베이스 표의 설계도를 작성하는 폴더이다.

---

### app/repositories/

데이터베이스에 직접 접근하여 데이터를 조회, 저장, 수정, 삭제하는 코드를 작성하는 폴더이다.

주로 다음과 같은 기능을 작성한다.

- 환자 정보 조회
- 새로운 환자 정보 저장
- 기존 환자 정보 수정
- 환자 정보 삭제
- 검사 결과 조회 및 저장

예를 들어 특정 환자의 ID를 이용하여 데이터베이스에서 환자 정보를 찾는 코드를 작성할 수 있다.

쉽게 말하면 `app/repositories/`는 데이터베이스에서 실제로 정보를 꺼내거나 저장하는 역할을 담당하는 폴더이다.

---

### app/schemas/

API로 들어오는 요청 데이터와 사용자에게 돌려주는 응답 데이터의 형식을 정의하는 폴더이다.

주로 Pydantic을 사용하여 다음 내용을 작성한다.

- 요청 데이터의 항목
- 응답 데이터의 항목
- 각 데이터의 타입
- 필수 입력값과 선택 입력값
- 잘못된 데이터가 들어왔는지 확인하는 규칙

예를 들어 환자를 등록할 때 이름은 문자열인지, 나이는 숫자인지 확인할 수 있다.

쉽게 말하면 `app/schemas/`는 API에서 주고받는 데이터가 올바른 형식인지 검사하는 폴더이다.

---

### app/services/

프로젝트의 주요 업무 규칙과 처리 순서를 작성하는 폴더이다.

주로 다음과 같은 기능을 작성한다.

- 입력된 데이터가 업무 규칙에 맞는지 확인
- 여러 데이터베이스 작업을 순서대로 처리
- 중복 데이터 확인
- 검사 결과나 환자 상태에 따른 처리
- repository의 여러 기능을 조합하여 하나의 업무 완성

예를 들어 새로운 환자를 등록할 때 이미 등록된 환자인지 확인한 후 저장하도록 처리할 수 있다.

쉽게 말하면 `app/services/`는 실제 업무를 어떤 규칙과 순서로 처리할지 결정하는 폴더이다.

---

### app/apis/

사용자가 보낸 API 요청을 가장 먼저 받는 폴더이다.

주로 다음과 같은 내용을 작성한다.

- API 주소 설정
- GET 요청 처리
- POST 요청 처리
- PUT 또는 PATCH 요청 처리
- DELETE 요청 처리
- service 기능 호출
- 처리 결과 반환

예를 들어 사용자가 환자 목록을 요청하면 API가 요청을 받은 뒤 service를 호출하여 환자 정보를 가져오고 결과를 반환한다.

쉽게 말하면 `app/apis/`는 사용자와 백엔드 프로그램이 만나는 접수 창구이다.

## 4. 데이터베이스 연결 설정

### app/core/db/databases.py

`databases.py`는 FastAPI 프로젝트와 데이터베이스를 연결하는 파일이다.

주로 다음과 같은 내용을 작성한다.

- 데이터베이스 접속 주소 불러오기
- SQLAlchemy Engine 생성
- 데이터베이스 Session 생성
- 모든 모델이 상속받을 Base 클래스 정의
- API 요청이 끝난 후 Session 종료

기본적인 데이터베이스 연결 구조는 다음과 같다.

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import DeclarativeBase, sessionmaker


class Base(DeclarativeBase):
    pass


engine = create_engine(
    "데이터베이스 접속 주소"
)


SessionLocal = sessionmaker(
    bind=engine,
    autoflush=False,
    autocommit=False,
)
```

각 항목의 역할은 다음과 같다.

- `engine`: Python 프로그램과 데이터베이스를 연결하는 통로
- `SessionLocal`: 데이터 조회와 저장 작업을 수행하는 작업 공간
- `Base`: 모든 SQLAlchemy 모델이 상속받는 기본 클래스

실제 데이터베이스 주소는 `.env` 파일에 저장하고, `config.py`에서 불러와 사용할 수 있다.

데이터베이스 비밀번호가 포함될 수 있는 `.env` 파일은 일반적으로 GitHub에 올리지 않는다.

## 5. SQLAlchemy ORM 모델 작성 방법

SQLAlchemy ORM을 사용하면 데이터베이스의 테이블을 Python 클래스로 작성할 수 있다.

예를 들어 환자 정보를 저장하는 모델은 다음과 같이 작성할 수 있다.

```python
from sqlalchemy import String
from sqlalchemy.orm import Mapped, mapped_column

from app.core.db.databases import Base


class Patient(Base):
    __tablename__ = "patients"

    id: Mapped[int] = mapped_column(
        primary_key=True,
        autoincrement=True,
    )

    name: Mapped[str] = mapped_column(
        String(100),
        nullable=False,
    )

    age: Mapped[int] = mapped_column(
        nullable=False,
    )
```

각 코드의 의미는 다음과 같다.

- `Patient`: 환자 테이블을 나타내는 Python 클래스
- `__tablename__`: 실제 데이터베이스 테이블 이름
- `id`: 각 환자를 구분하는 기본키
- `name`: 환자 이름을 저장하는 컬럼
- `age`: 환자 나이를 저장하는 컬럼
- `nullable=False`: 반드시 값이 입력되어야 한다는 의미

다른 테이블과 연결할 때는 외래키를 사용할 수 있다.

```python
patient_id: Mapped[int] = mapped_column(
    ForeignKey("patients.id"),
    nullable=False,
)
```

이 코드는 현재 테이블의 `patient_id`가 `patients` 테이블의 `id`와 연결된다는 의미이다.

ERD에 있는 테이블과 컬럼을 확인한 뒤, 각 테이블의 모델을 `app/models/` 아래에 Python 파일로 작성한다.

## 6. Alembic 마이그레이션 방법

Alembic은 SQLAlchemy 모델의 변경 사항을 실제 데이터베이스에 반영하는 도구이다.

Python 모델만 작성한 상태에서는 실제 데이터베이스에 테이블이 만들어지지 않는다.

Alembic으로 마이그레이션 파일을 생성한 뒤 데이터베이스에 적용해야 한다.

### 6.1 Alembic과 모델 연결

`alembic/env.py`에서 SQLAlchemy의 `Base`를 가져온다.

```python
from app.core.db.databases import Base

target_metadata = Base.metadata
```

작성한 모델도 Alembic이 확인할 수 있도록 불러와야 한다.

```python
from app.models.patient import Patient
```

모델을 불러오지 않으면 Alembic이 새로 작성한 테이블을 찾지 못할 수 있다.

### 6.2 마이그레이션 파일 생성

모델 작성을 완료한 후 다음 명령어를 실행한다.

```bash
uv run alembic revision --autogenerate -m "create initial tables"
```

마이그레이션 파일은 다음 폴더에 생성된다.

```text
alembic/versions/
```

### 6.3 데이터베이스에 적용

생성된 마이그레이션을 실제 데이터베이스에 적용한다.

```bash
uv run alembic upgrade head
```

`head`는 가장 최신 마이그레이션 상태를 의미한다.

현재 적용된 마이그레이션은 다음 명령어로 확인할 수 있다.

```bash
uv run alembic current
```

마이그레이션 기록은 다음 명령어로 확인할 수 있다.

```bash
uv run alembic history
```

## 7. API 구현 흐름

API 요청은 일반적으로 다음 순서로 처리된다.

```text
사용자
↓
apis
↓
schemas
↓
services
↓
repositories
↓
models
↓
database
↓
사용자에게 응답
```

환자 등록 API를 예로 들면 다음과 같다.

### 1단계: 사용자 요청

사용자가 새로운 환자 정보를 서버에 보낸다.

```json
{
  "name": "김철수",
  "age": 55
}
```

### 2단계: APIs

`app/apis/`에서 사용자의 요청을 받는다.

```text
POST /patients
```

### 3단계: Schemas

`app/schemas/`에서 이름이 문자열인지, 나이가 숫자인지 확인한다.

### 4단계: Services

`app/services/`에서 이미 등록된 환자인지 확인하는 등 업무 규칙을 처리한다.

### 5단계: Repositories

`app/repositories/`에서 SQLAlchemy를 사용하여 환자 정보를 데이터베이스에 저장한다.

### 6단계: Models

`app/models/`에 작성된 환자 테이블 구조를 기준으로 데이터를 저장한다.

### 7단계: Database

실제 데이터베이스의 환자 테이블에 정보가 저장된다.

### 8단계: 응답

저장이 완료되면 등록 결과를 사용자에게 돌려준다.

## 8. 전체 정리

각 폴더의 역할은 다음과 같다.

```text
app/apis/
사용자의 요청을 받는 곳

app/schemas/
요청과 응답 데이터의 형식을 검사하는 곳

app/services/
업무 규칙과 처리 순서를 담당하는 곳

app/repositories/
데이터베이스를 조회하고 수정하는 곳

app/models/
데이터베이스 테이블 구조를 정의하는 곳

app/core/
환경설정과 데이터베이스 연결을 관리하는 곳
```

전체 API 처리 흐름은 다음과 같다.

```text
사용자 요청
→ API
→ Schema
→ Service
→ Repository
→ Model
→ Database
→ 사용자 응답
```

SQLAlchemy는 데이터베이스 테이블을 Python 클래스로 작성할 수 있도록 도와준다.

Alembic은 SQLAlchemy 모델의 변경 사항을 실제 데이터베이스에 적용할 수 있도록 도와준다.
